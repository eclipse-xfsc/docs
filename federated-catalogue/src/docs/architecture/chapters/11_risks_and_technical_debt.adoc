== Risks and Technical Debt

Every system that goes into production carries known imperfections.
Pretending otherwise would be dishonest; hiding them in an issue tracker would make them invisible to exactly the people who need to weigh them.
This chapter is the architectural honesty page: it names the risks we know about and the technical debt we have consciously accepted, explains why each exists, and describes what would resolve it.

Two reading hints help to interpret this chapter correctly:

* **A listed risk is a managed risk.** The entries below are not defects discovered by accident — most of them are documented consequences of deliberate architecture decisions (see <<section-design-decisions>>). Naming a trade-off here means it was seen, weighed, and accepted with open eyes, usually with a defined path to close it.
* **This chapter stays conceptual.** Day-to-day tracking of individual defects and work items lives in the project's issue tracker and backlog. This chapter describes the architectural themes behind them, so that a reader can judge the residual risk of the delivery without reading source code.

The inventory was compiled from source-code markers, the consequence sections of the architecture decision records, and internal review findings.
It is thorough but not provably complete; project management should cross-check it against its own risk register.

=== Risks

A _risk_ here means: a property of the current architecture that could cause harm — security exposure, data loss, operational surprise — if the surrounding assumptions stop holding.

==== Trust and verification posture

The catalogue's core promise is that the credentials it stores are trustworthy.
The current verification pipeline delivers a deliberately staged version of that promise, and it is important to understand which stage a given deployment is on.

These concerns make up this picture:

* **Verification is off by default.** Cryptographic signature verification is switched off in the default configuration (a deliberate decision, recorded as ADR 3, to keep development and evaluation deployments frictionless).
A default deployment therefore proves that stored credentials are _well-formed and unmodified_, but not that they were _issued by who they claim_.
The risk is that an operator ships the default without realising what it does and does not guarantee.
* **Trust chains are not checked to full depth.** Even with verification enabled, certificate chains embedded directly inside credentials are rejected rather than validated, and externally referenced trust anchors are checked for expiry only — full certification-path building and revocation checking are not yet implemented.
In plain terms: a revoked issuer certificate would currently go unnoticed.
* **Participant-scoped authorization is designed but not yet enforced.** Role-based access control is enforced within the service itself; the designed permission model (ADR 5) goes further, and the additional restriction of operations to the participant they belong to is not yet enforced everywhere.
* **Incomplete issuer key material produces unhelpful errors.** When an issuer publishes incomplete key material, one verification path skips the affected keys with only debug-level logging and ends in a generic "no matching key" error that does not name the root cause — issuer-side misconfigurations become hard to diagnose.
* **Identity resolution defaults to a public demo service.** The default configuration resolves issuer identities through a public, best-effort demonstration service on the open internet — adequate for evaluation, but a production federation must point identity resolution at infrastructure it controls, both for availability and because that service sits directly on the trust-establishment path.
* **The tamper-evidence seal has a narrower blind spot.** The distinction between an _infrastructure failure_ and a genuine _non-conformance verdict_ is now carried in a structured part of the stored result that the seal covers, so that discriminator is tamper-evident. The seal still excludes the general free-text report portion used for detailed diagnostics, which remains unprotected.

[cols="3,4,3", options="header"]
|===
|Concern |Why it matters |Path to resolution

|Signature verification off by default
|Default deployments prove integrity, not authenticity
|Operator awareness; a stricter development profile turns signature checking on, but the trust-anchor checks that give it meaning (ADR 3) must be enabled separately — no shipped configuration does both

|Incomplete certificate-path and revocation checking
|A revoked or improperly chained issuer certificate would not be detected
|Implement full certification-path validation for both embedded and referenced trust material

|Participant-scoped authorization not yet enforced
|Access control is coarser than the designed permission model
|Complete the enforcement of the model designed in ADR 5

|Unhelpful errors on incomplete issuer key material
|Issuer-side misconfiguration surfaces as a generic mismatch; the root cause is visible only in debug logs
|Name the root cause in the error instead of silently skipping affected keys

|Issuer-identity resolution defaults to a public demo service
|An external dependency outside the federation's control sits on the trust path
|The override mechanism exists (a local resolver) and the local development stack already uses it; the demo deployment and the hand-maintained manifests still inherit the public default, so operators of those paths must configure it deliberately

|Tamper-evidence seal on validation results excludes the free-text report
|The infrastructure-failure vs. non-conformance discriminator is now sealed; the general free-text diagnostic detail is not
|Extend the seal to cover the remaining free-text report; needs a dedicated security review
|===

==== Credential-format migration

The catalogue recently completed a hard cutover from the older Gaia-X credential generation ("Tagus") to the current one ("Loire") — the background and rationale are recorded in ADR 9.
The cutover is deliberately non-graceful: credentials in the legacy format are no longer recognised as credentials — they are accepted as unverified generic data instead, so participants must re-issue them in the new format to regain verified status.
That silent downgrade is itself part of the risk: an uploader receives no clear signal that their legacy credential was not treated as one.
This was the right architectural call (carrying two verification stacks indefinitely would have doubled the attack surface and the maintenance cost), but it transfers a real burden onto federation participants: as long as issuing tooling for the new format remains immature across the ecosystem, participants with legacy credentials face a migration effort that the catalogue itself cannot shorten.

Two adjacent tensions deserve attention:

* **Ecosystem generality.** The verification stack is currently strongest for Gaia-X-shaped credentials. If support for standards-conformant credentials from _other_ issuers were dropped entirely, the catalogue would become a Gaia-X-only component — which would contradict its original vision as a generic federation building block. This is a strategic boundary to watch, not a defect.
* **Tooling friction at the standards edge.** The JSON-LD processing library in use rejects certain constructs that the new credential format legitimately produces, which can result in a presentation being accepted but yielding _no extracted claims_ — a silent partial failure. This is a known limitation of the library; a regression test pins the failing shape, and the credential format permits an alternative encoding that avoids it.

==== Ontology and schema evolution

The catalogue understands the semantics of stored credentials through a bundled ontology — a machine-readable vocabulary of the Gaia-X conceptual model.
Two evolution risks follow from how this bundling works today (both rooted in the decisions of ADR 9):

* The bundled ontology is a hand-curated subset of the official one, trimmed to the constructs the resolution logic can process. If future spec releases start relying on constructs outside this subset, type resolution could degrade _silently_ — entries would stop being classified correctly without any error surfacing.
* On an existing deployment, newly added ontology files are silently ignored at restart, because the schema store is only populated on first initialisation. An operator upgrading an installation could reasonably believe they have imported a new vocabulary when they have not.

Both risks share the same character: nothing breaks visibly at the moment the assumption fails.
The mitigation direction is therefore the same for both — turn silent degradation into loud, operator-visible signals.

==== Graph-store operations

The catalogue keeps its queryable knowledge graph in a pluggable backend, and the backend can be switched at runtime (ADR 18).
This flexibility is valuable — it is what allows a federation to choose its graph technology — but it concentrates operational risk in the switching and rebuilding procedures:

[cols="3,4,3", options="header"]
|===
|Concern |Why it matters |Path to resolution

|Backend switch relies on a single pre-flight probe
|The probe is the only check that the target backend actually works; at a later restart the stored choice is applied again without re-probing and with at most a log warning — if the chosen backend is no longer reachable, the service still starts, reports the problem only through its health signal and log, and query requests fail with server errors until an operator intervenes
|Harden the probe; re-validate the stored choice at startup and fail visibly

|Backend switch does not migrate data
|The new store starts empty; a full rebuild from the primary store is required
|Deliberate design (the primary metadata store remains the source of truth); operators need the rebuild step in their runbook

|Enrichment can duplicate managed structure
|The catalogue's own reserved vocabulary is already shielded at the enrichment boundary, but users can still hand-create metadata in ordinary vocabulary that overlaps with what the catalogue manages automatically, causing soft inconsistencies
|Extend the existing guard rail from the reserved vocabulary to catalogue-managed structure in general (ADR 15 describes the enrichment concept)

|Repeated enrichment replaces rather than accumulates
|A second enrichment of the same asset silently discards the first one's queryable metadata — a consequence of the graph store's replace-by-subject write model
|Open product question: decide whether accumulate semantics are wanted, then either change the write model or document the replace behaviour prominently
|===

The common theme: the graph store is treated as a rebuildable projection of the primary metadata store — a sound architectural principle — but the operational instrumentation around switching and rebuilding still lags behind the principle.

==== Ambiguous verification results

One verification endpoint distinguishes a missing _asset_ from an asset without verifiable credentials (the former is a proper not-found error, and "nothing to verify" is reported as an explicit failure with a named reason rather than a pass) — but it does not make the same distinction for a missing _version_ of an existing asset.
Requesting a version that never existed yields the same "nothing to verify" answer as a version that exists but carries no credentials, so a caller who mistypes a version number sees a plausible-looking result instead of an error.
This is a small surface with an outsized trust impact — verification APIs, of all places, should never let a mistake masquerade as a meaningful answer.
The resolution is straightforward: check version existence before looking up credentials.

=== Technical Debt

_Technical debt_ is the engineering equivalent of a mortgage: a shortcut taken deliberately to deliver value sooner, with the understanding that interest accrues until it is repaid.
The entries below are ordered by theme, not severity; none of them endangers the correctness of the delivered functionality today, but each one makes some future change slower or riskier than it should be.

==== Leftovers from the credential-stack migration

The migration described in the risk section above (and in ADR 9) removed an entire family of signature libraries from the core service — but the surrounding tooling has not fully caught up:

* Two auxiliary credential-signing tools (used for performance testing and local development) still reference the removed library family and need to be rewritten against the current formats, or retired.
* Fixture generation for the current format relies on a purpose-built in-house signing script rather than the production issuing tooling — a deliberate separation for deterministic test fixtures, but one that means the fixture path and the production path must be kept in step by hand.
* Caching of externally fetched documents on the RDF-import path uses an ad-hoc file store rather than the caching mechanism idiomatic to the tooling; the JSON-LD context and identity-document fetches already use idiomatic caches.

The first two items live in the periphery (tooling, fixtures) and their interest rate is developer confusion; the caching shortcut is reachable from the credential-ingestion path itself, where it changes how external documents are fetched but not what verification concludes.

==== Extension-point gaps

Two of the system's extension points carry known gaps:

* Trust-framework bundles that declare validation capabilities the runtime does not support are registered _inactive_ — the only signal is a single warning line in the startup log, easy to miss among routine output, so an operator can believe a configured framework is active when it is doing nothing. As with the ontology risks above, the fix is to surface the failure where operators actually look.
* Some query languages are intentionally unsupported on some graph backends; these are documented feature gaps, not defects, but they constrain backend choice for federations with specific query needs.

==== API-contract hygiene

Three themes:

* **Specification drift.** The published API specification has accumulated small mismatches against the implementation: response fields that are declared but never populated, nullability declarations that do not match reality, and endpoint documentation that describes behavioural changes only in shared schema definitions where clients are unlikely to look.
Individually each is minor; collectively they erode the specification's authority as the contract between the catalogue and its integrators.
* **No documentation-sync step in the process.** A behavioural change to a published endpoint can currently be merged with the specification updated but the architecture documentation untouched — nothing ties the two together.
This chapter itself is part of the answer, but a lightweight definition-of-done rule ("API behaviour change ⇒ documentation sync") would address the root cause.
* **Layering slips.** Wire-format constants are defined inside the verification domain layer, where transport concerns do not belong.
A cleanup spanning more than one file, listed here because layering violations tend to multiply when the first one is tolerated.

==== Test debt

The test suite carries a handful of known soft spots:

* Several disabled tests awaiting fixes — some annotated as disabled (one at class level, silencing a whole group), and some commented out entirely, which does not even show up as "skipped" in test reports.
* One missing positive-path coverage area in asset storage (a dated marker where the graph-storage success scenario was never added).
* Accuracy tests that pre-date the final claim-parsing implementation.
* In the acceptance-test suite, test-purpose tags are applied to scenarios but nothing partitions or gates on them — the suite is actually partitioned only by configuration profile. This one matters more than it sounds, because purpose labels that promise a safety net which never runs cause engineers to trust the wrong one before merging.

==== Dependency and operational currency

Three items:

* **Deferred major upgrades.** High-severity dependency vulnerabilities are remediated as they surface, caught by a scheduled and release-time vulnerability scan rather than a pre-merge gate; the enduring item is the major-version upgrades of the underlying framework and database, consciously deferred to a dedicated effort rather than bundled into feature work — a scheduling decision that keeps upgrade risk contained but must not be deferred indefinitely.
* **Re-validation sweep not wired in.** A periodic re-validation sweep for stored data against current schemas exists as a self-contained, tested component, but no code path in the running service creates or triggers it — enabling it is a development task, not a configuration change.
* **Sweep work-sharing assumes a fixed replica count.** When the sweep _is_ enabled, it partitions its workload by a _configured_ instance count, not by the number of instances actually running — a deployment running fewer replicas than configured silently never revalidates the surplus partitions.
Aligning the configured count with reality (or deriving it automatically) closes the gap.

==== Documentation and deployment hygiene

Three further items, unrelated to each other but sharing the same character — nothing wrong today, but each one erodes a promise the documentation or deployment tooling implicitly makes:

* **Database image versions diverge between delivery paths.** The relational-database and identity-provider image versions referenced by the packaged deployment chart and those in the hand-maintained deployment manifests have drifted apart, and the graph-database image pinned by the local development stack has drifted from the one in those manifests (the chart itself ships no graph-database image). The paths should track the same versions, or the divergence should be a deliberate, documented choice rather than an accident of separate maintenance.
* **Several architecture diagrams have no editable source.** A number of diagrams in the architecture documentation exist only as rasterised images; without the original diagram source, updating one means redrawing it from scratch rather than editing an existing file.
* **Development-only credentials are stored in cleartext.** The deployment chart's default configuration values contain development-only credentials in cleartext — convenient for a throwaway evaluation deployment, but a template an operator could copy into something more permanent without noticing what it carries forward.

=== Relation to the decisions chapter

Some entries a reader might expect here are deliberately _not_ listed, because they are scope decisions rather than risks: functionality that was consciously descoped or deferred within the project window (including one refactoring that was cancelled precisely _because_ it was judged too risky to execute late in the delivery) is recorded in the project's decision log — and, where architecturally significant, as an ADR in <<section-design-decisions>>.
The rule of thumb: if it was a choice, it is documented as a decision; if it is a consequence we live with, it is listed here.
